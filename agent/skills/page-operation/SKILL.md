# 页面操作

## 什么时候用

- 用户要的是**界面动作**：打开菜单、点新建、填表单、提交、关闭弹窗、切换标签页。
- 数据查询、字段确认、改数据仍然用 `graphql_execute`，不要用页面点击绕路。

## 步骤

1. 不确定用户是否打开了页面时，先调 `page_status`：

   - `online: false` → 直接告诉用户"请先打开系统页面再让我操作"，不要重试。
   - `path` 告诉你用户当前在哪个路由，据此判断需不需要先导航。

2. 调 `page_operate`：

   ```json
   {
     "instruction": "进入系统管理 → 用户管理，搜索 admin，点击第一行的编辑按钮",
     "max_steps": 12
   }
   ```

3. 指令写法：

   - 写**目标 + 关键文案**，用页面上真实可见的中文；不要写 CSS 选择器或坐标。
   - 一次只做一件事。多步任务按"先到哪、再做什么"顺序写，不要一次塞五个目标。
   - 不要让它打开站外链接或新窗口。

4. 结果处理：

   - `success: true`：把 `data` 里的页面状态转述给用户，必要时再查一次数据确认落库。
   - `success: false`：区分原因——
     - `用户拒绝了本次页面操作`（仅在开启确认策略时出现）：不要重试，问用户是否要继续；
     - `页面操作超时` / `页面正在执行上一个操作`：告诉用户稍后再试；
     - `页面未连接`：提示用户打开页面。

## 安全边界

- 默认**不弹确认框**（`VITE_AGENT_PAGE_CONFIRM=never`）；执行前会自动收起右下角的智能助手抽屉。
  需要更保守时，前端可改成 `risky`（命中删除/提交等词才确认）或 `always`。
- 页面操作**不受** `AGENT_TOOL_READONLY` 限制（那个开关只管 GraphQL）。要整体关闭用 `AGENT_PAGE_OPERATE=false`。
- 即便不弹确认，删除、审批、支付类动作也只做用户明确要求的，不要自行扩大范围。
- 模型只看到脱敏后的页面文本（手机号、邮箱、身份证、银行卡已替换），不要向用户复述这些占位符。
- 涉及批量操作时，先做一条，让用户确认结果，再做剩下的。

## 常见失败

| 现象 | 处理 |
| --- | --- |
| 找不到按钮 | 让用户确认页面是否已打开到对应菜单；或先用更宽泛的描述定位 |
| 点到了提示条/遮罩 | 让指令带上"关闭提示后"或"在弹窗中"等上下文 |
| 虚拟表格滚动不到目标行 | 拆成"搜索关键词缩小结果"再操作 |
